# Клиентский renderer матрицы

Оригинал исследован через `javap -c -p` из SHA-проверенного BETA26 JAR:
`TileInfusionMatrixRenderer`, `ModelCube`, `TileInfusionMatrix.doEffects`.
Полный вывод остаётся вне Git в `/workspace/reference/javap`.

`InfusionMatrixRenderer` строит восемь простых кубов программно. Исходный
`ModelCube(int)` описывает куб 16×16×16 вокруг нуля и render scale 1/16;
renderer уменьшает его до 0.45 блока и ставит в каждую комбинацию ±0.25
относительно центра матрицы. Это объясняет геометрию без переноса исходного
model-класса или файлов модели. Дополнительного центрального куба оригинал
не рисует.

Подтверждённые численные правила:

- `renderInfusionMatrix:69..108`: повороты вокруг Y `(cameraAge % 360)*startUp`,
  X `35*startUp`, Z `45*startUp`.
- `255..293`: множитель колебания
  `min(6, 1 + (stability<0 ? -stability*.66 : 1)*min(craftCount,50)/50)`.
- `313..568`: восемь кубов; активные смещения по осям
  `sin((cameraAge+axisIndex*10)/{15,14,13})*.01*startUp*multiplier`;
  поворот на 90° вокруг каждой оси с index=1.
- `589..1006`: активная полнояркая additive-оболочка RGB(.8,.1,1),
  alpha `(.2+.1*sin((cameraAge+x*2+y*3+z*4)/4))*startUp`.
- `doEffects:207..372`: craftCount повышается на 1 при crafting; после
  crafting уменьшается на 2 с ограничением сверху 50. startUp растёт на
  `max(startUp/10,.001)` до 1; после отключения умножается на .9 до нуля.
- `drawHalo`: только при crafting, 10/20 треугольных лучей по настройке графики,
  `Random(245)`, белая середина с alpha `255*(1-craftCount/500)` и прозрачные
  пурпурные концы. Рост ограничен первыми 50 ticks. Порт использует существующий
  vanilla `RenderType.dragonRays` с SRC_ALPHA/ONE и без записи глубины.

Старт и счётчик ведутся в слабом клиентском кэше renderer, не в серверной
матрице. Между кадрами используется интерполяция. При возврате к ранее скрытой
матрице кэш догоняет время по текущему синхронизированному active/crafting;
он не восстанавливает историю смены флагов, которой клиент не располагает.
Значения не участвуют в расходе ресурсов, сохранении или завершении ритуала.

Оригинальные `infuser_normal/ancient/eldritch.png` и их layout UV здесь **не
перенесены**. Используется уже существующий в ветке `block/pedestal_side`,
поэтому рисунок поверхностей и различия трёх типов алтаря остаются art gap.
Новых PNG, скопированных моделей и дизассемблированных исходников в Git нет.
Минимальное расширение glow-куба на 0.0005 блока и clamp отрицательной alpha
halo — технические меры рендера порта, не новые исходные механики. Render AABB
расширен на один блок, чтобы повёрнутые детали и лучи не пропадали у края экрана.
Opaque-детали рисуются одним проходом до glow; renderer не использует завершённый
VertexConsumer после переключения типа буфера.

Изолированный `InfusionMatrixClientEvents` регистрирует BE renderer, не меняя
общий `ThaumcraftClientEvents`. Для мира требуется
`InfusionMatrixBlock.getRenderShape() == ENTITYBLOCK_ANIMATED`; baked item-модель
остаётся доступна. Защитная проверка renderer прекращает рисование при MODEL,
исключая удвоение статической геометрии при неполной интеграции.

Проверка в этой задаче: компиляция двух новых клиентских классов JDK21 через
`javac -proc:none -sourcepath ''` с кэшированным NeoForge classpath в отдельный
`/workspace/reference/infusion-matrix-renderer-classes`; без Gradle.
Настоящий игровой кадр и ритуал должны проверяться клиентским прогоном root.
