## 2. Устройство оригинальных големов BETA26

### 2.1 Конструкция, материал и свойства

Оригинал разделяет `IGolemProperties` и живую сущность. Конструкция состоит из **материала, головы, рук, ног и одного дополнения**, отдельно хранится ранг. У каждого каталога есть числовой ID, текстовый ключ, требования исследований, компоненты и traits; у частей дополнительно есть модель и необязательная функция. Материал задаёт `healthMod`, броню, базовый урон, основной материал и механизм. Не следует заменять это системой произвольных атрибутов, придуманной для порта.

`GolemProperties` упаковывает ID материала/головы/рук/ног/дополнения и ранг в `long`. Свойства собираются в порядке **материал → голова → руки → ноги → дополнение**. Противоположные traits **взаимно гасятся**: если противоположное свойство уже присутствует, оно удаляется, а новое не добавляется. Это отличается от правила «последняя часть побеждает». Повторное появление того же trait учитывается через множество, поэтому порядок сборки существенен.

В официальном API определены 19 traits:

`SMART`, `DEFT`, `CLUMSY`, `FIGHTER`, `WHEELED`, `FLYER`, `CLIMBER`, `HEAVY`, `LIGHT`, `FRAGILE`, `REPAIR`, `SCOUT`, `ARMORED`, `BRUTAL`, `FIREPROOF`, `BREAKER`, `HAULER`, `RANGED`, `BLASTPROOF`.

Подтверждённые противоположные пары: `CLUMSY ↔ DEFT`, `HEAVY ↔ LIGHT`, `FRAGILE ↔ ARMORED`. Остальные свойства нельзя объявлять несовместимыми по одному названию. Список исходных материалов — дерево, железо, глина, латунь, таумий и пустотный металл; конкретные ID, требования, ингредиенты и числа берутся из статической регистрации исходного `GolemProperties`, а не из вики другой версии Thaumcraft. В эталонном JAR отдельного `ConfigGolem` нет. Подтверждённый стартовый `WOOD` имеет `healthMod=6`, `armor=2`, `damage=1` и `LIGHT`; `BASIC` руки не добавляют traits. Поэтому базовый деревянный голем имеет 16 HP и множитель навигации 1.2 и допускается печатью Pickup (не имеет `CLUMSY`).

Подтверждённый встроенный каталог материалов из `GolemProperties.<clinit>`:

| Legacy ID | Материал | Health modifier | Броня | Базовый урон | Traits материала |
|---:|---|---:|---:|---:|---|
| 0 | `WOOD` | 6 | 2 | 1 | `LIGHT` |
| 1 | `IRON` | 20 | 8 | 3 | `HEAVY`, `FIREPROOF`, `BLASTPROOF` |
| 2 | `CLAY` | 10 | 4 | 2 | `FIREPROOF` |
| 3 | `BRASS` | 16 | 6 | 3 | `LIGHT` |
| 4 | `THAUMIUM` | 24 | 10 | 4 | `HEAVY`, `FIREPROOF`, `BLASTPROOF` |
| 5 | `VOID` | 20 | 6 | 4 | `REPAIR` |

Это исходные параметры материала до модификации traits/рангом. Урон применяется только при `FIGHTER`; `healthMod` не является итоговым максимальным здоровьем. В Core реализован расход только начальной деревянной конструкции: 3× `plank_greatwood`, 2× `mechanism_simple`, 1× `mind@0`. Это сумма тела (2 base + mech), ног WALKER (base + mech) и головы BASIC (mind@0). Ранг не меняет стоимость. Для остальных конфигураций Core явно отказывает в расчёте, пока их ингредиенты не перенесены; универсального каталога расходов и работающего Golem Press пока нет.

### 2.2 Подтверждённые характеристики и обучение

По `EntityThaumcraftGolem.updateEntityAttributes`, `getGolemMoveSpeed`, `getTotalArmorValue` и `addRankXp`:

| Правило | Исходное вычисление |
|---|---|
| Максимальное здоровье | `10 + material.healthMod`; при `FRAGILE` целая часть от `health * 0.75`; затем `+ rank` |
| Броня | `material.armor`; при `ARMORED` целая часть `max(armor * 1.5, armor + 1)`; при `FRAGILE` целая часть от `armor * 0.75` |
| Урон | Без `FIGHTER` равен 0; иначе `material.damage`, при `BRUTAL` — `max(damage * 1.5, damage + 1)`, затем `+ rank * 0.25` |
| Базовый movement attribute | `0.3` |
| Множитель скорости AI | `1 + rank * 0.025 + LIGHT * 0.2 - HEAVY * 0.175 - FLYER * 0.33 + WHEELED * 0.25` |
| Рабочий радиус дома | 32 блока, при `SCOUT` — 48 |
| Follow range | 40, при `SCOUT` — 56 |
| Высота шага | `0.6`, для `WHEELED` — `0.5` |
| Обучение | Только на сервере и только при `SMART`; максимальный ранг 10 |
| Порог следующего ранга | `(rank + 1)² * 1000 XP`; исходный вызов повышает максимум один ранг |
| Постепенное восстановление | Все големы восстанавливают 1 HP каждые 100 ticks; `REPAIR` сокращает интервал до 40 |

Эти формулы — поведение BETA26. Поддержка trait в Core-каталоге ещё не означает перенос его полного эффекта в игре: например, `FLYER` требует отдельной навигации и управления полётом, `RANGED` — реальной атаки и снаряда.

### 2.3 Изготовление и сборка

В дистрибутиве есть `golem_builder`, `TileGolemBuilder`, GUI сборщика, `ItemGolemPlacer`, `GolemProperties.generateComponents`, рецепт/исследования големантии. Расчёт компонентов конструкции должен быть чистым Core-правилом; списание ингредиентов, эссенции, исследования и выдача предмета относятся к серверному адаптеру сборщика.

Не приравнивать правильный перечень компонентов к готовому survival-изготовлению. Пока не сверены весь цикл `TileGolemBuilder`, стоимость/время/эссенция, multiblock, контейнер и исходные рецепты, эти пункты остаются отдельной работой. Предмет создания минимального голема нужен для проверяемого появления и сохранения; его доступность через творческий режим не подтверждает изготовление в выживании.

### 2.4 Печать → задание → AI

Оригинальная печать — **запись на стороне блока**, идентифицируемая позицией и гранью (`SealPos`), а не самостоятельный неподвижный моб. `ISealEntity` хранит тип, область, приоритет, цвет, владельца, блокировку и чувствительность к редстоуну; `ISeal` определяет поведение. Контракт содержит `tickSeal`, `canGolemPerformTask`, `onTaskStarted`, `onTaskCompletion`, `onTaskSuspension`, `onRemoval`, сохранение и GUI. Фильтры, переключатели и область выделены дополнительными интерфейсами.

Печать периодически создаёт задания. `Task` содержит ID, тип цели (**блок = 0**, **сущность = 1**), `SealPos`, цель, назначенный UUID голема, `reserved`, `suspended`, `completed`, приоритет, lifespan, произвольные данные и связь с `ProvisionRequest`. API задаёт исходный lifespan **300 секунд**; `setReserved` добавляет 120, `setCompletion` — 1. `ServerEvents.worldTick` на серверной END phase вызывает cleanup **раз в 20 ticks**, затем печати обрабатываются каждый tick. Нельзя уменьшать lifespan на каждый Minecraft tick и называть это паритетом. Исходные setters увеличивают lifespan при обоих значениях boolean, что необходимо учитывать при проверке буквальной совместимости.

`TaskHandler` ведёт задачи раздельно по измерениям. Для выбора отдельно рассматриваются задания на блок и сущность; отбрасываются зарезервированные задачи и задачи, явно назначенные другому UUID. Оценка сортировки:

```text
score = squaredDistance(golem, target) - priority * 256
```

Меньшее значение выбирается раньше. Следовательно, исходный приоритет меняет расстояние на 256 единиц квадратной дистанции; это не абсолютное правило «всегда самый большой приоритет». Расстояние вычисляется до центра целевого `BlockPos`; для сущности берётся её текущая floored позиция. При равном score стабильного глобального tie-breaker в оригинале нет: остаётся порядок обхода concurrent map. Sorting сам не фильтрует `completed/suspended`; проверки распределены между AI и cleanup. Задание дополнительно проходит проверки конкретной печати, цвета, требуемых/запрещённых traits, рабочего радиуса и достижимости. По `Task.canGolemPerformTask` несовпадающие **ненулевые** цвета исключают работу; 0 действует как общий цвет.

AI оригинала разделён на `AIGotoEntity`, `AIGotoBlock`, `AIGotoHome`, общую основу `AIGoto`, следование владельцу и боевые задачи. В рабочем режиме задания на сущность имеют приоритет AI 3, на блок — 4, возвращение домой — 5. Это отдельный порядок от приоритета самой печати. `AIGoto` имеет cooldown 5, счётчик перемещения до 1000 ticks, повторную прокладку пути каждые 5 ticks, pause и callback начала задания. После достижения цели действие выполняет **печать**, а не универсальный AI. При отмене/просрочке вызывается callback приостановки; задание удаляется из рабочего набора. Недостижимая цель не должна удерживать голема навсегда.

Первая подтверждённая механика передвижения — `AIGotoHome`: начальная задержка 10 проверок, затем 50; движение начинается при расстоянии до дома в квадрате ≥ 5 и продолжается при > 3, если нет задачи и путь существует. Если расстояние в квадрате > 1024, выбирается промежуточная точка к дому с диапазонами 16 по горизонтали/7 по вертикали. Это не случайное бесцельное блуждание. Кастомные node rules `PathNavigateGolemGround/Air` ещё требуют отдельного переноса.

Обнаруженная исходная ошибка: gate заблокированной печати сравнивает UUID владельца голема через `UUID.equals` со строковым owner печати. Корректное сравнение UUID со строкой в адаптере следует документировать как исправление BETA26, а не выдавать за побайтовое повторение исходного поведения.

В `Task.java` код сериализации заданий закомментирован. Поэтому нельзя утверждать, что BETA26 сохраняет активный маршрут/задачу через рестарт. Долговечны сущность и печати; очередь работы должна восстанавливаться их логикой. Сохранение случайного указателя на живую Java-сущность в новый формат NBT было бы ошибкой архитектуры порта.

### 2.5 Исходный набор печатей и автоматизация

В JAR подтверждено наличие следующих реализаций; таблица **не означает, что их поведение уже полностью исследовано или перенесено**:

| Оригинальные классы | Назначение для следующего исследования |
|---|---|
| `SealPickup`, `SealPickupAdvanced` | Сбор выброшенных предметов, область и фильтры |
| `SealFill`, `SealFillAdvanced` | Вкладывание переносимых предметов в контейнер |
| `SealEmpty`, `SealEmptyAdvanced` | Извлечение из контейнера |
| `SealProvide`, `SealStock` | Заявки снабжения и поддержание запаса |
| `SealGuard`, `SealGuardAdvanced`, `SealButcher` | Защита, выбор целей и забой |
| `SealUse` | Применение предмета/взаимодействие |
| `SealHarvest` | Сельскохозяйственная работа |
| `SealBreaker`, `SealBreakerAdvanced`, `SealLumber` | Разрушение блоков и лесозаготовка |

Исследованные первые операции: `SealPickup` раз в 5 ticks рассматривает только лежащий на земле предмет без pickup delay и создаёт максимум одно задание за scan; forbidden trait — `CLUMSY`. При исполнении повторно проверяет вместимость/фильтр, передаёт stack в `IGolemAPI.holdItem` и обновляет реальный остаток; XP за pickup не начисляется. Базовый фильтр — пустой blacklist, совпадение metadata/NBT включено. `SealFill` проверяет работу раз в 20 ticks, создаёт задачу на контейнер и использует `dropItem`/`holdItem` для передачи и возврата остатка; за фактическую передачу начисляется 1 XP. При отсутствии item handler исходный Fill может выбросить предмет перед печатью. Установленный факт «в JAR есть `SealHarvest`» не определяет алгоритм зрелости растений, повторной посадки, расход семян, взаимодействие с правами и лутом — эти детали ещё необходимо сверить по конкретному классу и вспомогательным методам.

Оригинальный переносимый инвентарь — предметы в руках сущности: **одна переносимая стопка**, при `HAULER` — **две**. `holdItem` возвращает остаток; `dropItem` только изымает stack и сам не выбрасывает его в мир. Нельзя автоматически давать обычному голему сундук на 27 слотов. Исходный empty-slot insert допускает oversized stack и alias исходного объекта; перенос использует копии и реальный max stack size как явно отмеченную защиту от некорректного состояния 1.21.1. Фильтры и точные ограничения остальных печатей проверяются отдельно.

### 2.6 Сохранение и управление

В `EntityThaumcraftGolem` подтверждены NBT-поля `props`, `homepos`, `gflags`, `rankXP`, `color`; базовый owned construct и стандартная LivingEntity сохраняют свои поля, включая владельца и экипировку. В `SealEntity` подтверждены `pos`, `face`, `type`, `priority`, `color`, `locked`, `redstone`, `owner`, `area` и custom/toggle данные. Точный старый формат не следует смешивать с обязательным форматом новых сущностей Minecraft 1.21.1.

В JAR есть `ItemGolemBell`, `GolemInteractionHelper`, GUI печатей и GUI сборщика. Полные взаимодействия колокольчика, подбор голема в предмет, назначение дома, следование, окраска, разрешения владельца и клиентские индикаторы требуют отдельной сверки. Подсказка предмета или команда разработчика не заменяет исходный интерфейс управления.

## 3. Аудит существующего проекта на базе main

Статусы ниже относятся к исходной базе `a428083`, до изменений этого направления. **Пригодно** означает существующий механизм, который можно использовать; **частично** — есть связанные данные/примеры без системы M10; **отсутствует** — профильная реализация големов не найдена. «Проверено чтением» не означает новую игровую проверку.

| Подсистема | Состояние базы | Повторное использование и ограничение |
|---|---|---|
| Регистрация сущностей | Пригодно; голем отсутствует | `registry/ThaumcraftEntities` уже подключён в `ThaumcraftPort`; есть `AlumentumProjectile`. Применить тот же DeferredRegister-подход; M10 entry допускается в изолированном `GolemModule`, чтобы избежать конфликтов общих файлов |
| Регистрация предметов/creative | Пригодно; профильные предметы отсутствуют | `ThaumcraftItems`, `ThaumcraftCreativeTabs`; небольшое добавление предмета создания, позже колокольчика/печатей |
| Регистрация атрибутов живого моба | Отсутствует для M10 | Alumentum — снаряд, а не образец Mob. Нужен обработчик `EntityAttributeCreationEvent` |
| NBT блоков и предметов | Пригодно | `saveAdditional/loadAdditional(HolderLookup.Provider)`, `ContainerHelper`, `DataComponents.CUSTOM_DATA/BLOCK_ENTITY_DATA`; не копировать старую 1.12 NBT API |
| Сохранение сущности голема | Отсутствует | Нужны `addAdditionalSaveData/readAdditionalSaveData` поверх vanilla сохранения UUID, позиции, здоровья и экипировки |
| Серверные world data | Пригодно | `ThaumcraftAuraSavedData` показывает per-dimension `SavedData`. Печати получают отдельное хранилище, без записи в файлы ауры |
| Networking | Пригодно; M10 payload отсутствуют | `ThaumcraftNetworking`, `StreamCodec`, `PacketDistributor`, серверная обработка. Видимые поля сущности лучше передавать штатным `SynchedEntityData` |
| Инвентари и меню | Пригодно | `ArcaneWorkbenchBlockEntity`, `ResearchTableBlockEntity`, `SmelterBlockEntity`, `PedestalBlockEntity` используют vanilla `Container`/`ContainerHelper`; есть `AbstractContainerMenu` и шаблоны серверных проверок |
| Универсальный item capability bridge | Отсутствует в проверенных регистраторах | Не обнаружен общий `RegisterCapabilitiesEvent`/`Capabilities.ItemHandler` адаптер. Реализовывать локально в M10 при переходе к печатям, учитывать vanilla контейнеры |
| Транзакции предметов | Частично | `NeoForgeTheorycraftItemTransaction` — полезный пример plan/commit; `LegacyInfusionRitualLedger` — учёт оплаченного результата. Не использовать специфичную исследовательскую или инфузионную модель как инвентарь голема |
| Исследования големантии | Частично | `BuiltInResearchCatalog` уже содержит `GOLEMANCY`, `BASEGOLEMANCY`, материал/части/печати и их зависимости; это каталог, а не рабочая прогрессия и рецепты сборщика |
| Рецепты/материалы | Частично | Существуют метаданные слитков/самородков/пластин, arcane/infusion Core-правила и адаптеры. Рецепты M10 и сборщик отсутствуют; новые общие рецепты согласовать по владельцам |
| Модели/текстуры/анимации | Отсутствует для M10 | Есть общая клиентская регистрация `ThaumcraftClientEvents`, renderer снаряда/блоков. Golem/seal модели, текстуры, сборщик и анимации в базе не найдены |
| Локализация M10 | Отсутствует в активных EN/RU таблицах | Общие `en_us.json`/`ru_ru.json` существуют; добавлять узкие ключи и отдельно обозначать временный визуал |
| Core тесты | Пригодно | Самостоятельные `main`-тесты с Java assertions/явными проверками; `tools/run_core_parity.sh` компилирует весь Core через `javac --release 21`, запускает перечисленные классы |
| Gradle / Java / NeoForge | Пригодно | Java 21, `net.neoforged.moddev 2.0.146`, NeoForge 1.21.1, объединённые `src/main/java` и `src/neoforge/java`; runs `client`, `server`, `data` |
| Сервер/клиент smoke | Пригодно как инфраструктура | CircleCI запускает настоящий `runServer`; `tools/client_smoke.sh` и `ThaumcraftSmokeAudit` проверяют предыдущие сценарии. Готового игрового сценария големов/GameTest набора на базе нет |

Изменения общей алхимии, исследования или инфузии не требуются для появления и навигации первого голема. Исходные каталоги исследований и материалы использовать повторно; автономную разработку M10 не блокировать ожиданием полного M07.

## 4. Архитектура переноса: независимые компоненты A–F

Следующие границы — проектное решение адаптации к **NeoForge 1.21.1**. Планируемый компонент не считается реализованным до появления кода и проверки, записанной в журнале.

### A. Основа голема

**Core** хранит immutable-конфигурацию конструкции и вычисляет traits/характеристики. Контракт реализации: `port.core.golem.GolemDesign(long packed)`, `defaultWood/fromLong/toLong`, доступ к материалу/частям/рангу, `withRank/traits/hasTrait/stats/components`; `GolemStats` хранит вычисленные значения. Core не импортирует `net.minecraft` и не хранит `Level`, `Entity`, `ItemStack` или навигатор. Серверная сущность `entity/ThaumcraftGolem` наследует vanilla `PathfinderMob`; владелец — UUID, дом — `BlockPos`, ранг/XP, цвет и рабочие flags — явные поля. Игровые свойства и допустимые значения восстанавливаются из одного Core-источника.

Жизненный цикл: загрузка конфигурации → валидация каталога → восстановление базового entity NBT → пересчёт атрибутов → запуск серверных целей. Новая сущность получает свойства **до** `addFreshEntity`; предмет расходуется только после фактического добавления сущности. UUID никогда не генерируется повторно при обычной загрузке NBT. Повторное применение характеристик не должно лечить голема до полного здоровья.

Долговечны construction, owner, home, rank XP, color/flags и переносимые stacks. Runtime-цель и путь не записываются как ссылки на объекты. Ошибочная конфигурация должна обрабатываться явно и безопасно: нельзя обращаться к массиву отрицательным legacy byte или выдавать бесплатный голем за повреждённый предмет. Конкретная политика обработки фиксируется тестом.

Синхронизация: конструкция, цвет/flags и только необходимые видимые данные — `SynchedEntityData`; предметы в руках — штатная экипировка; GUI получает проверенный серверный snapshot. Клиент не назначает задания и не изменяет stacks. Изолированный `golem/GolemModule` подключает DeferredRegister entries и атрибуты одним вызовом из `ThaumcraftPort`; существующие entries других подсистем не переносятся и не дублируются. Отдельный клиентский обработчик регистрирует renderer. Предмет — `item/GolemPlacerItem`, первое передвижение — отдельный `GolemHomeGoal`.

### B. Части и улучшения

Каталог материалов и каталог каждой группы частей отделены от выбранной конструкции. Текстовые ключи устойчивы для логики порта; legacy ID сохраняются для битовой совместимости и проверки оригинальных предметных данных. Сначала поддерживается фиксированный BETA26 каталог; расширяемый публичный API для сторонних модов не является условием первого работающего голема.

Core должен проверять допустимость ID/ранга, выполнять исходное гашение traits и рассчитывать список компонентов с реальными количеством и вариантами материала. **Требование исследования** и **наличие ингредиента в мире** — разные проверки. Адаптер переводит Core ingredient spec в registry item/tag/metadata predicate и повторно проверяет их перед оплатой.

Сборщик — отдельные block, block entity, menu и screen. Core рассчитывает предложение конструкции и стоимость; сервер владеет входными слотами и оплаченной работой; выход выдаётся ровно один раз. Изменение GUI после начала изготовления не должно превращать уже оплаченную деревянную конструкцию в металлическую. Восстановление незавершённой сборки требует отдельного checkpoint, а не повторного списания компонентов.

### C. AI, выбор и исполнение задания

Разделить четыре роли: **данные задачи**, **выбор/резервирование**, **навигация**, **исполнение конкретной печати**. Core содержит проверяемые сортировку и state transition; NeoForge слой разрешает UUID цели, проверяет загруженный мир и строит путь. Очередь принадлежит одному серверному измерению, изменяется в основном серверном потоке.

Предлагаемые состояния исполнения: поиск → резервирование → движение → действие → завершение; отдельные исходы отмена/приостановка/просрочка. Они выражают уже существующие BETA26 `reserved/suspended/completed`, а не вводят новый игровой режим. Резервирование атомарно по task ID/UUID голема. Два голема не выполняют одну и ту же выдачу. До действия повторно проверяются цель, печать, фильтр и фактическая вместимость.

Обрыв пути, исчезновение цели, смерть/выгрузка голема и удаление печати освобождают зависимую runtime-работу. Повторная попытка ограничена подтверждёнными исходными cooldown/счётчиками. Защитный технический лимит не должен телепортировать голема, создавать предмет или помечать работу выполненной. Бой и follow-owner прерывают рабочую навигацию; после прерывания голем заново проверяет право на задачу. Точные правила оригинального возобновления требуют отдельного теста перед включением полной системы.

Наземная навигация используется для первого подтверждённого варианта. `CLIMBER`, `WHEELED`, `FLYER` получают отдельную адаптацию исходных ограничений; наличие enum без рабочего пути не считается переносом передвижения этого типа.

### D. Печати

Нужны: реестр типов печатей, immutable `SealPos`, persistent `SealConfiguration`, серверный `SealService`, runtime task board и клиентский слой отображения. В 1.21.1 ключ измерения — `ResourceKey<Level>`, а не старый числовой dimension ID. На одной позиции допустимы разные грани; ключ только из `BlockPos` теряет исходное поведение.

Сохранение печатей — отдельный per-level `SavedData`, индекс по chunk/позиции/грани. Печати работают только в загруженных чанках; поиск работы не должен создавать chunk ticket или загружать дальний контейнер. Запись данных и runtime регистрация при загрузке/выгрузке разграничены, чтобы одна печать не размножалась после рестарта.

Настройки содержат исходные priority/color/owner/locked/redstone/area, whitelist/blacklist/filter/toggles по возможностям типа. Конкретная печать определяет генерацию задач, required/forbidden traits и действие. Минимальная вертикаль для автоматизации — **Pickup → руки голема → Fill → сундук**, затем Empty, Provision/Stock и остальные типы. Общие callbacks сохраняют семантику `ISeal`; прямое сканирование всех предметов каждым големом вместо очереди печатей не выдавать за перенос этой системы.

### E. Инвентарь и автоматизация

Для первого голема использовать штатные hand slots, сохраняя одну/две доступные переносимые стопки по `HAULER`. Item adapter отвечает за item/component equality, stack max, остатки и dirty state. План размещения проверяет фактическую вместимость, но результат определяется реальным вставлением/извлечением на сервере.

Для произвольных контейнеров нужен локальный NeoForge bridge `Capabilities.ItemHandler` с выбранной гранью и vanilla fallback там, где это необходимо. Существующие алхимические транспортные порты работают с эссенцией и не являются item API. Не делать общий рефакторинг контейнеров M04–M07 ради первых големов.

Обязательный инвариант каждого переноса:

```text
source_before + golem_before + destination_before + world_items_before
  = source_after + golem_after + destination_after + world_items_after
```

Сравнение выполняется по item и значимым components. Нельзя выдавать желаемое количество по результату simulate, если actual operation приняла меньше. Извлечённый остаток возвращается в исходный доступный инвентарь/руки; явно определённый fallback — реальный drop, который учитывается в сумме. Повторный callback для завершённого task не переносит предмет второй раз. Смерть, подбор голема и выгрузка не должны одновременно сохранять и выбрасывать одинаковые stacks.

Сельское хозяйство вводится после сверки `SealHarvest`, `SealUse`, `GolemInteractionHelper`: зрелость, break/use, реальные drops, расход семян, возможность повторной посадки и разрешения. Нельзя заменять это бесплатным созданием урожая или универсальной процедурой «пшеница выросла».

### F. Интерфейсы и визуализация

Отдельные server menu/client screen для сборщика и печатей используют существующие `ThaumcraftMenus`/screen registration. Пакеты настройки содержат ID открытого меню, позицию/грань и изменяемое поле; сервер повторно проверяет расстояние, владельца, блокировку и диапазон. Никакой клиентский пакет не принимает готовый `ItemStack` результата, XP или произвольный class name печати.

Первый renderer должен позволять видеть живую сущность и анимацию движения; временная модель указывается как временная. Далее — сборная модель по частям, исходные текстуры материалов, поворот головы/рук, переносимый предмет, рабочие/боевые анимации, цвет, ранг, emotes и отображение печатей с колокольчиком. Список traits в tooltip не заменяет видимость состояния в мире. Новые ключи сразу добавляются симметрично в EN/RU.

## 7. Проверки и тестовые сценарии

### 7.1 Core, Java 21

Запускать существующий `bash tools/run_core_parity.sh`; новые содержательные тесты добавлять в список минимальным изменением. Assertions должны сравнивать результаты с конкретными исходными значениями и отрицательными примерами; напечатанный без проверок PASS не является тестом.

1. Все материалы, головы/руки/ноги/дополнения: исходные ID, traits, исследования и ингредиенты.
2. `long → properties → long`: rank, граничные ID, нулевые поля, некорректные байты и свободные биты; отсутствие silent alias.
3. Противоположные traits: взаимное гашение, повторный trait и эффект порядка частей.
4. Здоровье/броня/урон/скорость/radius: rank 0 и 10, fragile/armored/brutal/scout, порядок целочисленного округления.
5. Обучение: обычная голова без SMART, серверная SMART, точный порог, перенос остатка XP, один ранг за вызов, cap 10.
6. Task selector: score, расстояние против приоритета, UUID reservation, разные типы целей, цвет 0/ненулевой, удаление/истечение.
7. Модель переноса: полная/частичная вместимость, одинаковый item с разными components, нестандартный max stack, повторное завершение и сохранение общего количества.

### 7.2 NeoForge и настоящий сервер

Один осмысленный полный `compileJava processResources`, затем JAR и `runServer` на Java 21. Если зависимость или сеть блокирует Gradle, записать точный URL/код/первую ошибку и не объявлять compile успешным. Запуск сервера подтверждается реальным готовым миром и отсутствием crash, затем отдельно проверяется M10.

1. Spawn через предмет: расход ровно одной штуки в survival; Creative не расходует; препятствие/отказ добавления не расходует предмет.
2. Сущность жива, имеет исходные атрибуты и достигает дома по обычному маршруту с препятствием; смена свойства не лечит её.
3. Сериализация в настоящий `CompoundTag`, восстановление новой сущности: construction, owner, home, rank/XP, color/flags, здоровье и обе руки. Повторное чтение не размножает stacks.
4. **Сохранить мир → штатно остановить сервер → запустить тот же мир**: тот же UUID, ровно один голем, те же данные и предметы. Прямая NBT round trip проверка не заменяет этот сценарий.
5. Выгрузить/загрузить chunk: одна печать на грань и одна сущность; очередь восстанавливается без старых ссылок/reservations; дальние чанки не загружаются поиском работы.
6. Два голема и одна цель; цель исчезла/сдвинулась/сменила stack, сундук переполнился, маршрут закрыт, печать удалена, сервер перезапущен в пути: нет зависания, потерь или двойного выполнения.
7. Полная Pickup/Fill вертикаль и реальное сравнение инвентарей/ItemEntity до и после, включая смерть голема с грузом.

Для автоматизации игровых проверок использовать существующую серверную инфраструктуру и изолированные тесты M10; GameTest требует отдельного подключённого run/config и не считается существующим по одному имени класса. Тестовый probe допускается только при проверке реального мира и должен падать при невыполненном инварианте.

### 7.3 Клиент

### M10.4 — подтверждённый маршрут в контейнер

`GolemSeals.Type` разделяет PICKUP/FILL в общем per-level SavedData; существующий TaskBoard обслуживает оба типа целей. Fill создаёт block task раз в20 ticks и новое доступное задание при старте старого. `GolemFillGoal` использует priority4 и AIGotoBlock thresholds, поэтому Pickup3 и Home5 сохраняют исходный порядок.

`GolemContainers` получает sided `Capabilities.ItemHandler.BLOCK` без кеширования через переустановку блока. Vanilla chest/barrel/furnace обслуживаются их штатными NeoForge capabilities. Назначение требует simulate room-for-some; завершение использует actual remainder, а не обещанный simulate count. Остаток возвращается в руки; компоненты и max stack limits определяет настоящий handler. При отсутствии handler исходный Fill выбрасывает предмет на выбранной грани; unloaded destination/вторая половина сундука этим случаем не считаются.

После положительного actual transfer начисляется1 SMART XP, только сервером; порог `(rank+1)^2*1000`, один rank за вызов и cap10. Это не выдача XP для Pickup или головы BASIC. В переносе намеренно нет XP за нулевой фактический перенос, даже если нестабильный handler предварительно обещал место.

Сохраняется прежняя узкая поверхность: empty blacklist, неизменяемые через GUI defaults, стандартный деревянный placer, временные item icons. UI/настройки, `pexist`/limits/whitelist и redstone ещё не реализованы. Точные игровые проверки и инструкции перезапуска: [протокол](GOLEM_VALIDATION_2026_10_18.md), текущий статус: [журнал](lanes/golems.md).

### M10.5 — фильтры Pickup/Fill и минимальное меню (продолжение)

Подтверждение: `SealFiltered`, `SealPickup`, `SealFill`, `InventoryUtils.findFirstMatchFromFilterTuple`, `InventoryUtils.countStackInWorld`, `SealBaseContainer` из официального BETA26 JAR с уже зафиксированным SHA. Локальные `javap -c -p` материалы остаются вне Git. Базовые Pickup/Fill имеют один ghost-slot, пустой blacklist разрешает всё, пустой whitelist запрещает всё. По умолчанию pmeta/pnbt включены, ore/mod выключены. Строгое совпадение современного ItemStack проверяет item + components без учёта количества. Переключатели игнорирования metadata/NBT, ore/mod и pexist этим срезом не реализуются.

Pickup не имеет stack-size limiter. Fill применяет положительный размер только в whitelist и вычитает уже существующие matching items контейнера. Ноль означает отсутствие лимита. Сначала выбирается первая подходящая рука; неподходящая mainhand не блокирует подходящую HAULER offhand. Количество повторно вычисляется непосредственно перед фактической вставкой; оставшиеся у голема предметы включают и withheld budget, и реальный remainder capability. Это защищает общий запас при двух ранее зарезервированных заданиях.

Обнаруженная особенность оригинала: `InventoryUtils.countStackInWorld` проходит дальше только для `ItemStack.isEmpty()==true` и пропускает непустые stacks (bytecode offset58 `ifeq91`). Поэтому при отсутствии handler оригинальный Fill фактически считает запас на земле нулевым. Срез сохраняет этот дефект явно: лимит ограничивает каждый drop, а не общий запас на земле. Исправление этого поведения требует отдельного решения о parity, его нельзя незаметно назвать исходным строгим ground-stock limit.

`SealFilter` хранит собственную копию ghost count1; наружу возвращаются копии. SavedData сохраняет `bl`, `Items` slot0 и `Sizes` slot0/Size int, современные components кодируются через registry-aware ItemStack. Старые строки без настроек получают прежний accept-all default. Конфигурация отменяет задания/leases этой печати. Дополнительный непостоянный instance UUID защищает открытое меню от изменения заново установленной печати на той же грани; старые задания и instance UUID не загружаются из NBT.

Меню — новый минимальный адаптер, не полный исходный Bell GUI. Повторное использование соответствующего предмета печати на своей занятой грани открывает его; Shift по-прежнему снимает печать. Ghost-копирование не расходует cursor/inventory. ЛКМ копирует cursor, ПКМ очищает, Shift-click inventory копирует образец; mode и ±1/±10 задают лимит Fill. Управление идёт штатными menu packets, размер синхронизируется двумя 16-bit DataSlot, сервер проверяет owner, dimension, distance8, живого игрока, loaded support, build permission и instance UUID. Bell, исходные GUI gestures, полный исходный art и survival-рецепты остаются отдельными задачами. Клиентский вид требует отдельной графической проверки.

### M10.6 — управление печатями, 19.10.2026

Официальные `SealEntity.tickSealEntity/isStoppedByRedstone` и `SealBaseContainer` подтверждают: приоритет GUI −5…+5, цвет0…16 (нулевой — wildcard), owner-lock и redstone-sensitive по умолчанию false. ### M10.10 — настраиваемая область Pickup, 19.10.2026

Исходники: `SealPickup implements ISealConfigArea`, `SealFill` этот интерфейс не реализует; `SealEntity` constructor/NBT и `GolemHelper.getBoundsForArea`; `SealBaseContainer` actions90…95. ## M10.18 — заявки снабжения: исходные правила, Core и серверный producer

Повторно изучены `thaumcraft.api.golems.ProvisionRequest`, все перегрузки `GolemHelper.requestProvisioning`, полные `SealProvide`/`SealStock`, `Task.setSuspended` и `ThaumcraftInvHelper.hasRoomFor` официального BETA26 JAR. Дампы `Provisioning.txt`/`Task.txt` только в `/workspace/reference/javap`, не в Git. Это исследование доступного байткода, не объявление закрытого кода автора открытыми исходниками.

Подтверждённые правила:

- Три разных получателя: seal, block+face, entity. Stock использует **block+face overload**, а не seal overload. Поэтому исходная проверка recipient seal traits/locked не применяется к Stock как к seal recipient. Политики современного получателя потребуется проверять явным адаптером, а не считать уже обеспеченными API.
- Конструктор копирует ItemStack. Ключ источника — hash строки адреса/грани или numeric entity ID и stack.toString с NBT; stack count входит в идентичность. `ui` по умолчанию0, caller discriminator отличает дополнительные запросы. Повторный request при contains не меняет имеющийся deadline. Начальный timeout — wall clock+10000ms; **каждый** `setLinkedTask`, включая null, устанавливает +120000ms.
- Provide имеет6 toggles: pmeta/pnbt=true, pore/pmod/psing/pleave=false. Stock имеет первые4, всегда whitelist и per-slot stack-size limiters; оба имеют9 slots и запрещают CLUMSY, required tags null. Наличие SMART не требуется.
- Stock каждые20ticks считает matching stock для каждого ghost slot, берёт `min(maxStack, desired-existing)`, затем только фактически помещающееся количество через simulated insertion. Нулевой desired не означает unlimited, как у Fill. Запросы и проверки не извлекают и не создают предметы.
- Provide проверяет список каждые20ticks, находит первый подходящий unlinked request в радиусе **distance²<4096**, проверяет provider filters и strict source stock (с reserve1 при pleave). Создаёт не более1 pickup task за проход. Для seal recipient priority берётся у получателя/lifespan10; для block/entity priority5/lifespan31000.
- Pickup имеет data0. После забора block/entity request создаёт delivery task data2/data1 соответственно, lifespan31000, наследует priority, связывается с тем же request. Seal recipient отдельного provider delivery task не получает. Проверка кандидата различает not carrying+canCarry на pickup и isCarrying на delivery, проверяет home range/recipient traits.
- Раз в100ticks Provide удаляет invalid, **unlinked**, suspended/completed-linked и просроченные заявки; условие timeout строго `< now`, равенство живое. Это не обычная очередь, где непривязанные заявки обязательно живут все10 секунд. `Task.setSuspended` стирает только свою ссылку; provider suspension callback отдельно отвязывает request. Полное выполнение исходника содержит повторные запросы при недостатке груза и ejection/insertion; эти inventory/AI действия ещё не перенесены в M10.18.

Реализация:

- `ProvisionRequest<K>` — типизированные цели/immutable exact key/count/ui, copied modern item identity в native adapter, timing/link/invalid. `GolemTask` вместо прежнего Object хранит `ProvisionRequest<?>`; остальные source setter rules не меняются.
- `ProvisionBoard<K>` — отдельная ephemeral очередь одного мира/серверного потока с dedup, source deadlines/sweep и взаимными ссылками. CAS по **object identity** predecessor защищает delivery от позднего pickup suspension, в том числе при совпадении task IDs. Close/sweep отменяют связанную работу, не трогая груз.
- `ProvisionRules` — Stock deficit/room, psing/pleave pickup budgets, strict provider radius и source factories pickup/delivery. Здесь нет вызовов Minecraft и нет инвентарных списаний.
- `GolemProvisioning` — серверный API, exact defensive ItemKey с real components, отдельный board на ServerLevel, unload close; Stock producer принимает9 policies и использует **существующий** `GolemContainers.handler` с loaded/double-chest guards и реальные sided ItemHandler capabilities. Используется только insert simulation; возвращается принятая часть, не insertion remainder. Публичных предметов/меню двух новых печатей ещё нет.

Осознанные adapters: полный immutable key вместо collision-prone hash/string identity; entity UUID вместо transient numeric ID; seal instance UUID защищает замену по той же грани; при1000 requests отклоняется лишний, исходник удаляет самый старый даже активный; late callback не отвязывает successor; снятая/просроченная заявка отменяет свой task, сохраняя реальные руки. Global sweep выполняется один раз/мир каждые100ticks, а не по случайному phase каждого Provide. В исходнике без Provide sweep вообще не исполнялся; в порте очередь ограничена и очищается независимо. Deadline остаётся wall clock, не Minecraft ticks; зависшее/приостановленное время мира не продлевает заявку.

Границы: этот срез переносит request lifecycle и реальный server producer дефицита, **не полный Provide/Stock gameplay**. Следующий этап —9-slot persisted policies/owner menu, typed seal placement/paid source recipe, provider selection и actual extraction→successor task→delivery через существующие leases/AI/recovery. Требуются native tests со всеми фазами, конкурирующими големами, свежим cap при доставке, снятием/изменением обоих seals, redstone/owner/color/traits/home/loaded guards и сохранением уже оплаченного груза. Запросы/leases не сериализуются: после рестарта регенерируются от печатей, руки голема уже сохраняются существующим NBT.
