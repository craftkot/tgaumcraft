## Правила продвижения и объединения веток — обязательно

1. `ROADMAP_RU.md` на `main` — **единственная официальная карта**. Активные рабочие ветки: `feature/alchemy` (M04, затем M05), `feature/research` (M07), `feature/infusion` (M06), `feature/golems` (M10). В каждом чате заранее выбрать **одну ветку**; `П` означает продолжение **в ней**, а не поиск другого этапа.
2. `main` использовать для **проверенного слияния PR**, а не для прямых feature-коммитов. Каждый чат коммитит только в свою ветку, не переписывает HEAD других веток и не делает force-push.
3. **Все четыре feature-ветки ведут назначенные этапы**: M04 🟡, M06 🟡, M07 🟡, M10 🟡 (четвёртая ветка `feature/golems` добавлена 18.10.2026). Разрешено **по одному жёлтому этапу на каждую активную ветку**, а не одна жёлтая строка на весь проект. Статус не даёт разрешения на слияние и не доказывает готовность. Перед новым подходом сверять HEAD и lane-журнал каждой команды.
4. Разделение файлов и общих изменений описано в [`analysis/PARALLEL_WORKFLOW_RU.md`](analysis/PARALLEL_WORKFLOW_RU.md). Файлы, касающиеся нескольких систем (CI, Gradle, registries, общие GUI/ресурсы, основной `ROADMAP_RU.md`), не править параллельно без согласования. Другую подсистему не менять просто ради удобства.
5. В рабочей ветке фиксировать прогресс **в своём** `analysis/lanes/alchemy.md`, `research.md`, `infusion.md` или `golems.md` (последний существует только в `feature/golems`), обновлять статус, SHA и следующую задачу. Главную дорожную карту `main` изменять только при согласованной интеграции, чтобы четыре команды не конфликтовали на одном файле.
6. Кандидат на слияние: **Pull Request из feature-ветки в `main`** с перечнем изменённых механизмов, CI, сохранений/NBT, регрессий и доказательств игровых тестов. **Не сливать автоматически без проверки/разрешения владельца.**
7. Перед каждым PR обновить ветку с актуальной `main`, разрешить конфликты предметно, повторить нужные тесты и проверить, что изменения другой ветки не потерялись. Если два PR трогают общие файлы — один интегрируется раньше, другой пересинхронизируется после.
8. По результатам принятой работы маркировать пройденную часть 🟢 только при выполнении критериев. `Core Parity` ≠ `NeoForge compile` ≠ `Minecraft gameplay`. Проваленный тест не превращать в успех без логов.
9. Никаких бесплатных ресурсов, имитационных рецептов, скрытых force-load чанков или выдуманных скриншотов. Совместимость сверять с Thaumcraft 6.1.BETA26. Цель — полный честный порт.
